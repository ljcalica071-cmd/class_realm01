1. CURRENT SYSTEM OVERVIEW

ClassRealm is a Flutter frontend-first Senior High School management-system prototype. The application uses Material UI, local in-memory mock data, role-based screens, and named Flutter routes. It demonstrates the intended school workflows but does not yet provide durable persistence, server-side authorization, real authentication, real RFID/device integration, or a production grading database.

The main architecture is:
- Flutter application bootstrap in lib/main.dart.
- Named routes in lib/routes/app_routes.dart.
- Shared in-memory singleton state in lib/data/mock_database.dart.
- User and academic entities in lib/models/user_model.dart and lib/models/academic_models.dart.
- Role screens under lib/features/{admin,teacher,student,parent}.
- Reusable visual components under lib/widgets/common.

The largest implementation surface is lib/features/teacher/screens/teacher_dashboard_screen.dart. It contains the teacher navigation shell and many feature renderers in one stateful widget, including classroom setup, classwork/assessment management, attendance, grading, gradebook, reporting, item analysis, lesson planning, materials, scheduling, and profile views.

The system is suitable for UI demonstration and workflow prototyping. It is not yet a complete school information system because most data is process-local and several screens display fixed or illustrative values instead of deriving them from a consistent academic record model.

2. CURRENT USER ROLES

Defined roles:
- Admin
- Teacher
- Student
- Parent

The role enum and account state enum are defined in lib/models/user_model.dart. Account states include active, pending, rejected, archived, pendingFirstLogin, and deactivated.

Admin:
- Has a dedicated dashboard and sidebar.
- Can view teacher/student/parent counts, teacher management, pending approvals, system statistics, profile, and settings placeholders.
- Pending teacher approval is represented in mock data and can be updated through MockDatabase.
- The implementation does not establish a robust permission guard around routes. A dashboard route can be opened independently of a server-issued session and role enforcement is primarily performed by the login transition.
- The documented boundary that Admin should not manage academic records is not enforced by a reusable authorization layer.

Teacher:
- Has the broadest implemented dashboard.
- Can view classroom setup, classwork/assessment creation, attendance, student management, exam checker, item analysis, grading, gradebook, reports, analytics, lesson planning, materials, schedule, notifications, and profile.
- Uses the logged-in teacher name in the current classroom/teacher areas, with mock data and fallback behavior.
- Most teacher operations mutate MockDatabase lists directly.

Student:
- Has a mobile-oriented portal with home, activities, quizzes/exams, notifications, and profile sections.
- Can enter the student assessment flow for QuizOrExamModel objects.
- Student identity is not consistently resolved from every screen; several profile and dashboard labels remain hardcoded to Juan Dela Cruz.

Parent:
- Has a mobile-oriented portal with overview, attendance, grades, notifications, and profile sections.
- Displays a linked student concept, but the current implementation uses hardcoded parent/student presentation values rather than resolving a general parent-to-many-student relationship.

3. CURRENT FEATURES

Authentication and onboarding:
- Login, registration, forgot-password, pending-account, and first-login routes exist.
- Mock authentication uses username/password values stored in MockDatabase.
- New teacher/student/parent registration UI exists, but there is no external identity provider or durable account store.
- Teacher-created student accounts can be created with a generated username and temporary password.
- Student first-login flow validates the temporary password and replaces it with a new password in memory.

Teacher academic and classroom features:
- Classroom setup includes school-year/class structure controls and classroom cards.
- Student management includes active/archived views, add/edit/view dialogs, soft archive/restore, deactivation/reactivation, and permanent deletion methods.
- Teacher academic setup and grading criteria are represented by UI and mock GradingCriteria values.

Assessment and classwork:
- Activities/assignments are represented by ActivityModel.
- Performance tasks use the same ActivityModel with isRequirement=true; the visible UI has been renamed toward Performance Task, but the model flag and legacy class/file names still use requirement terminology.
- Quizzes and examinations use QuizOrExamModel with questions, answer keys, points, schedule, duration, publication state, and result release state.
- A unified teacher Assessments & Classwork view now groups Written Work (WW), Performance Tasks (PT), and Examinations (EX), while older activity and quiz renderers remain in the same large dashboard file as unused/legacy code.
- Creation flows remain separate internally: activity modal, performance-task dialog, and quiz/exam question-builder dialog.

Student work and scoring:
- Student submissions are represented by StudentSubmission.
- Activity submission and teacher scoring UI exists in activity_submissions_screen.dart.
- Quiz/exam answer checking is performed locally against QuestionModel.correctAnswer.
- AssessmentResultModel records answers, score, total points, violations, release status, and teacher-review state.

Attendance:
- AttendanceRecord includes student, section, date, time-in, status, method, and isSynced.
- Seed data distinguishes RFID-style and manual attendance.
- Teacher attendance UI includes status summaries, filtering/search-related presentation, and manual status mutation.
- Offline/sync state is represented by SyncStatus and a mock toggle.

Academic support:
- Gradebook UI displays grading-period/class filters, WW/PT/EX weighting chips, category sections, score rows, and Export Grades.
- Item Analysis, performance analytics, reports, lesson planning, learning materials, schedule, notifications, and profile screens are represented in the teacher dashboard.
- Student and parent portals expose simplified views for activities, assessments, attendance, grades, schedule/materials, alerts, and profile.

4. CURRENT NAVIGATION/FLOW

Application entry:
- lib/main.dart starts ClassRealmApp and routes initially to the login screen.
- Routes are declared in lib/routes/app_routes.dart.

Login flow:
1. User enters credentials or selects demo credentials.
2. MockDatabase.authenticate searches the in-memory users/password data.
3. Pending accounts route to PendingAccountScreen.
4. Deactivated accounts show an error.
5. pendingFirstLogin accounts route to FirstLoginScreen.
6. Active users route by UserRole to the corresponding dashboard.

Teacher flow:
- TeacherDashboardScreen is a large StatefulWidget with sidebar index selection.
- The default selected index is Classroom Setup.
- The teaching navigation now exposes Assessments & Classwork as the combined classwork feature.
- The unified feature has WW, PT, and EX tabs.
- Create opens a chooser:
  - WW Activity / Assignment uses the activity input.
  - PT Performance Task uses the performance-task input.
  - WW Quiz / EX Exam uses the question-builder input.
- Gradebook is a separate dashboard section and reads assessment/activity lists for its displayed item groups.
- Student submissions are opened from activity cards.
- Student quiz/exam attempts are opened from student assessment surfaces.

Student flow:
- StudentHomeScreen uses bottom navigation for Home, Activities, Quiz/Exam, Alerts, and Profile.
- Activities are listed from MockDatabase.activities.
- Quizzes/exams are listed from MockDatabase.quizzesAndExams.
- Starting a quiz/exam pushes StudentAssessmentScreen.

Parent flow:
- ParentHomeScreen uses bottom navigation for Overview, Attendance, Grades, Alerts, and Profile.
- Drawer actions display schedule/contact/logout interactions.
- Linked-student content is mostly fixed presentation data.

Admin flow:
- AdminDashboardScreen uses a desktop sidebar.
- Teacher Management and Pending Approvals read MockDatabase user lists.
- Statistics and settings are present as dashboard destinations but are not equivalent to a complete administration backend.

5. CURRENT GRADING FLOW

Configured grading criteria:
- MockDatabase seeds GradingCriteria, including the intended Written Works 20%, Performance Tasks 50%, and Examinations 30% proportions.
- Teacher grading UI displays criteria and an update action.
- The displayed criteria are not currently a complete calculation engine.

Current data path:
1. Teacher creates an ActivityModel, QuizOrExamModel, or performance task.
2. The object is inserted into an in-memory list.
3. Student activity submissions or assessment results are inserted into separate in-memory lists.
4. The teacher can view/scoring-related screens.
5. Gradebook constructs display rows from activities and quizzes/exams.

Important limitation:
- There is no durable GradeRecord/QuarterGrade entity that combines all student scores.
- There is no complete formula that aggregates item scores by category, applies 20/50/30 weights, applies transmutation, and stores a published quarterly grade per student/subject/section.
- Assessment results and activity submissions are not consistently joined into Gradebook rows by student.
- Gradebook currently represents item structure and metadata more reliably than calculated student grades.
- Export is a UI action/placeholder rather than a verified file-generation pipeline.

6. CURRENT ASSESSMENT FLOW

Activity/assignment flow:
- The teacher can create an activity with title and description through the dashboard modal.
- ActivityModel stores instructions, subject, grade, section, deadline, maximum score, publication state, submission type, and counts.
- StudentSubmission stores an activity/exam ID, student, timestamp, attachment/text fields, score, max score, status, and feedback.
- Teacher can open activity submissions and score a submission with feedback.
- Submission maxScore is currently assigned in MockDatabase.submitActivity rather than consistently copied from the source activity's maxScore, creating a potential scoring mismatch.

Performance-task flow:
- The former requirement dialog creates an ActivityModel with isRequirement=true.
- The visible naming has been changed to Performance Task, but class names, callback names, model flag, and some internal semantics still contain requirement terminology.
- The input captures title, section, points, description, instructions/rubrics, submission type, deadline, and attachment placeholder.
- This is conceptually close to the intended PT workflow, but the model should eventually use an explicit assessment category/type instead of a boolean.

Quiz flow:
- CreateAssessmentFlowDialog provides quiz mode and an item/question builder.
- It supports question types from QuestionType, answer keys, choices, points, duration, target section, instructions, and schedule.
- New quizzes are inserted into quizzesAndExams.

Exam flow:
- The same creation dialog supports examination mode.
- The current UI provides ST1, ST2, and TE selection and uses title/category values to classify exams.
- QuizOrExamModel only stores isExam, so the exact exam subtype is inferred from title text in Gradebook. This is fragile and should become an explicit enum/category field.

Student assessment attempt:
- StudentAssessmentScreen requires rules acknowledgment.
- It displays a timer/rules concept and answer interface.
- On submit, it checks answers locally against the answer key and creates an AssessmentResultModel.
- The current student ID/name used for result persistence is hardcoded to usr_student_1/Juan Dela Cruz in the assessment screen.
- Results requiring teacher review are flagged for exams, but a complete teacher review/update path is not established.

11. FLOW OR LOGIC PROBLEMS

1. In-memory singleton state is the only source of truth. Restarting the app resets accounts, assessments, scores, attendance, and grades.
2. The logged-in student is not consistently used. StudentAssessmentScreen persists results for usr_student_1 and Juan Dela Cruz rather than reading currentUser.
3. Parent and student screens include hardcoded identity and academic labels, so a different authenticated account may see the wrong person.
4. Activity submission maxScore is hardcoded to 50.0 in submitActivity instead of using the ActivityModel maxScore.
5. GradingCriteria is displayed independently from the score/result collections; changing criteria does not recompute grades.
6. Gradebook grouping is partly inferred from strings. Exam names such as “Second”, “ST2”, “Term”, or “Final” determine sections instead of an explicit exam category.
7. ActivityModel.isRequirement is a boolean overloaded to mean Performance Task. This prevents future categories and makes “requirement” terminology persist in code.
8. AssessmentResultModel is stored separately from activitySubmissions, with no unified grade-item/result abstraction.
9. Anti-cheating violation rules are stated to students, but no event increments _violations.
10. A delayed local submit operation simulates processing but does not provide cancellation, retry, or durable submission semantics.
11. Exam results can be marked for teacher review, but the complete review/release state transition is not evident as a single connected workflow.
12. The teacher dashboard contains legacy and unified renderers in the same file. This increases maintenance risk and can lead to different behavior depending on which route/index is used.
13. Some navigation destinations are UI placeholders or report-style views with no underlying calculation/data pipeline.
14. Account status handling is local and route-based; direct route navigation is not protected by a centralized session/permission guard.
15. Section, subject, school-year, and grading-period values are commonly seeded or typed as strings rather than selected from consistent entities.

12. UI/UX PROBLEMS

- Teacher dashboard remains very large and dense, with many functions in one sidebar and one source file.
- Legacy labels and internal concepts remain alongside the newer unified Assessments & Classwork naming.
- Similar creation concepts use different dialogs and terminology.
- The visible grading system can imply that final grades are operational even though the calculation pipeline is incomplete.
- Empty states are inconsistent across teacher, student, and parent features.
- Success dialogs often confirm local mutation rather than a durable save.
- Some screens use fixed illustrative profile names and scores, which can reduce trust during demonstrations.
- Gradebook actions and rows are visually present but not all have functional export/edit/review behavior.
- Error handling is primarily modal and does not consistently identify whether a failure is validation, authorization, or persistence-related.
- A large amount of UI behavior is embedded in the teacher dashboard rather than reusable feature widgets.

13. RESPONSIVE DESIGN ISSUES

Good coverage:
- Login has separate desktop and mobile layouts and has already received overflow fixes.
- Student and parent portals use bottom navigation and generally mobile-first cards.

Risks:
- Admin and teacher dashboards use a fixed sidebar plus wide content areas and are strongly desktop-oriented.
- Teacher cards, filter rows, assessment rows, and gradebook structures can exceed narrow tablet/mobile widths.
- Wide Rows with action buttons are not consistently converted to Wrap, Column, or horizontally scrollable content.
- Data-heavy attendance, gradebook, item-analysis, and reporting areas need explicit small-screen behavior.
- Dialogs use fixed widths and large inset assumptions; mobile keyboard and viewport behavior need verification.
- Responsive behavior is based mainly on local widget layout decisions rather than a shared breakpoint policy.

14. IMPORTANT RECOMMENDATIONS

1. Establish a domain model before adding more UI:
   - SchoolYear, Term/GradingPeriod, Subject, Section, Enrollment, AssessmentItem, Submission, Score, GradeRecord, AttendanceSession, and ParentStudentLink.
2. Replace ActivityModel.isRequirement with an explicit AssessmentCategory or AssessmentType:
   - writtenWork, performanceTask, summativeTest1, summativeTest2, termExamination.
3. Use the same assessment-item abstraction for activities, quizzes, PTs, and exams, while retaining category-specific configuration such as question builder versus rubric/instructions.
4. Build a pure grading service first. It should calculate category percentages, 20/50/30 weighting, exam subweights, transmutation, rounding, missing-score rules, and publication state without depending on widgets.
5. Replace hardcoded current student/parent identities with currentUser and relationship lookups.
6. Make every submission and result reference the source item’s maximum score, section, subject, term, and student enrollment.
7. Add a repository/service boundary around MockDatabase now, even while remaining frontend-first. This will make later persistence replacement safer without adding Firebase or Supabase during this stage.
8. Centralize route/session/role guards and validate the current account before rendering each role dashboard.
9. Separate the teacher dashboard into feature screens/widgets to remove legacy duplicate renderers and reduce regression risk.
10. Define anti-cheating behavior explicitly for the target runtime. Web tab visibility and mobile lifecycle are different signals and should not be treated as one universal event.
11. Define offline sync semantics separately from visual SyncStatus: queued mutations, retry policy, conflict rules, timestamps, and user feedback.
12. Add focused tests around account creation/first login, category mapping, grading formulas, assessment submission, exam review, and role routing.
13. Use shared responsive components for dashboard sidebars, filter bars, card actions, table overflow, and dialog sizing.
14. Keep frontend-only scope explicit: mock persistence may be improved locally, but real services/hardware should be a separate implementation phase.

FINAL ASSESSMENT

The project already demonstrates the intended ClassRealm product shape and has a strong frontend prototype foundation. The most important gap is not the number of screens; it is the lack of a consistent academic data and grading pipeline connecting assessment creation, student submission, teacher scoring, category weighting, transmutation, publication, and parent/student display. The next engineering phase should prioritize domain/data correctness and testable grading logic before expanding additional UI modules or integrating real services.
